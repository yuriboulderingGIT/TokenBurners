# Site-reading audit — 20 November 2026

Reviewed commit `6020c14`. Seven defects were reproduced with offline HTTP fixtures; browser cases ran in headless Microsoft Edge through the real discovery implementation. One additional fixture demonstrates an existing host restriction. No public portals or paid models were called, and no production code was changed.

The existing suite passed: **226 passed, 6 skipped**. The diagnostic probes ran in two batches: **8 failing assertions and 3 passing checks** in total. Seven failing assertions reproduce defects; the eighth documents the unsupported API-subdomain case. The passing checks cover ordinary same-origin browser discovery, loading a CDN module, and the measured duplicate listing traversal.

The reproducible checks are in [site_read_reproductions.py](site_read_reproductions.py). They intentionally assert the desired behavior and fail on the reviewed code. They are outside the normal `tests/` collection. From a working project Python environment, run `python -m pytest output/site_read_reproductions.py -q -p no:cacheprovider`. Browser checks require installed Microsoft Edge; all page traffic is intercepted and handled by fixtures.

## Confirmed defects, in suggested repair order

1. **[P1] Browser discovery drops page cookies.** `brain/js_discover.py:262` fulfills responses with only status, content type and body. `PublicVisit` retains server cookies for its HTTP requests, but the browser never receives `Set-Cookie`. A listing whose JavaScript reads an anonymous session or CSRF cookie cannot initialize its search. In the fixture, the page sets `session=anonymous`, then fetches tenders only when that cookie is visible: discovery requests only `/list` and returns no feeds. Preserve cookie behavior between the browser and the isolated HTTP session. Probe: `test_browser_session_cookie`.

2. **[P1] Browser requests lose their requested headers.** `brain/js_discover.py:208` recreates GET requests through `fetch_page` without forwarding the observed request headers. `brain/public_search.py:24` passes only its own Cookie header. The fixture requests `Accept: application/json`; the HTTP request reaches the server with the default accept header, receives the HTML search form, and discovery finds no feed. Forward appropriate observed read headers, including content negotiation and anonymous anti-forgery headers, while maintaining origin/session isolation. Probe: `test_browser_requested_json_headers_are_forwarded`.

3. **[P1] Successful read-only POSTs are aborted in the browser.** `brain/js_discover.py:174–193` replays an eligible anonymous POST, then unconditionally aborts its browser route. A page that first queries configuration and then requests notices never performs the second operation. The fixture makes a read-only POST to `/api/query`, awaits its JSON, then fetches `/api/tenders`; only the first query reaches the HTTP layer. Fulfill accepted read-only responses to the browser, even when the response itself is not a tender collection. Probe: `test_browser_post_response_reaches_page`.

4. **[P1] Separate portals share one HTTP cookie jar.** `app/fetcher.py:70` creates one `httpx.AsyncClient` for every portal, and `app/fetcher.py:115` builds normal GETs using its shared cookies. Two monitored searches on the same host can overwrite session state. Reproduction: portal A selects buyer A, portal B selects buyer B, then A reads results with `buyer=B`. Rate limiting does not isolate sessions. Use independent cookie state per portal while retaining shared host request spacing. Probe: `test_cookie_isolation`.

5. **[P2] HTML `<base href>` is ignored.** `brain/run_recipe.py:198` resolves detail links against the response URL, and `brain/run_recipe.py:675` simply applies `urljoin`. The same assumption appears in learning and document-link resolution. For `/list` containing `<base href="/procurement/">` and `href="notice/1"`, Watchtower requests `/notice/1` instead of `/procurement/notice/1`. The fixture's valid notice becomes a 404 and the read fails. Resolve observed HTML links against the document's effective base, with destination validation retained. Probe: `test_html_base_url`.

6. **[P2] Duplicate IDs can pass both attach validation and the full health check.** `brain/learn.py:214` samples only the first three details. `app/health.py:87` accepts a distinct-ID ratio of exactly 90%, and skips uniqueness checks entirely below three tenders. `app/db.py:322` then silently keeps only the first tender for each ID. A ten-row fixture with distinct first three IDs and a collision in the final two rows passes attach and health but stores nine notices. Reject conflicting duplicate IDs before publishing; if overlapping pagination repeats a truly identical notice, handle that explicitly. Probe: `test_duplicate_after_first_three_rows`.

7. **[P2] Temporary errors on the initial fetch never get a scheduled retry.** `brain/learn.py:471` wraps HTTP failures as `AttachFailed`; `app/worker.py:212` marks the portal failed; `app/worker.py:99` excludes failed portals without a recipe from scheduling. A 503 after the fetcher's retries have been exhausted therefore requires a manual refresh, even though no model was called. The fixture ages the failed run and invokes the scheduler, which queues nothing. Preserve the transient HTTP failure category and permit bounded retries for pre-model failures. Probe: `test_first_fetch_transient_error_is_retried`.

## Measured performance problem

`validate_candidate` traverses the complete listing chain (`brain/learn.py:214`), then the worker starts a fresh full traversal (`app/worker.py:227`). A 50-page fixture generated **100 listing GETs** for validation plus the initial read. At the default 1.1-second spacing, those requests alone require at least **108.9 seconds**, before model calls, response latency, detail pages, or documents. Failed proposals can repeat the validation traversal again.

For browser-backed searches, discovery also revisits the site when validation opens `SearchPages`, then again for the worker's first read. Reusing fetched listing responses and the anonymous visit within a single attach attempt could reduce this work substantially; a later scheduled refresh should still obtain fresh data. The measurement probe is `test_measure_repeated_listing_walk`.

## Support and test-input problems

- **GET APIs on an API subdomain are blocked by design.** `brain/js_discover.py:202` allows cross-origin scripts but aborts cross-origin GET data requests. A page at `portal.example` fetching `api.portal.example/tenders` yields no feed. Public POST eligibility already permits certain child subdomains, making the GET and POST support inconsistent. A carefully scoped policy for observed public API hosts is needed; simply dropping origin checks is not a suitable fix. Probe: `test_browser_get_api_subdomain`.
- **The configured BOAMP input cannot represent a complete collection within the current reader's limits.** `testset/portals.yaml` supplies an unfiltered API URL with `limit=3` and no offset. The saved fixture advertises 1,728,870 notices. The reader cannot advance a missing numeric paging parameter, and adding an offset alone would still exceed the 100-page limit. Use an explicit, bounded monitoring query and a suitable page size. This is already reflected in an existing regression test and should not be interpreted as a fresh model failure.
- **The historical report is not a measurement of this checkout.** Its suspected 4,096-token truncation issue has already been addressed: `brain/llm.py:31` now sets 16,384 and recognizes output-limit failures. The current test for truncated responses passed. Live attachment rates still need remeasurement after fixes; this audit does not claim these fixtures explain every historical failed portal.
