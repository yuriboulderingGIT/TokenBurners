**What the algorithm currently does.**

1. `POST /portals` registers the address and queues a read. A worker prevents concurrent reads for the same portal.
2. The learner fetches the entry URL, checks for login/challenge pages, and distinguishes HTML from JSON. For HTML it supplies the model a compact page excerpt and up to 60 links, with at most two navigation iterations.
3. The model proposes a recipe: XPath or JSONPath selectors, detail links, document links, locale, and pagination. HTML proposals get bounded retries and a stronger-model attempt. JavaScript discovery can observe public GET feeds and some anonymous POST searches.
4. Candidate validation traverses the listing chain, but extracts at most the first three tender details. An attachment-run GET cache reduces repeated fetching between validation and the first full read.
5. The full reader follows up to 100 listing pages, extracts details, normalizes fields, and downloads documents. HTML and JSON share the same overall recipe model. Some portal-specific document helpers supplement the generic reader.
6. Health checks examine IDs, title coverage, field regressions, count drops, and document failures. A passing read is stored; absent old notices are marked closed. A recipe failure can trigger repair, and a repaired recipe must pass a full read before replacing the old one.
7. Normal refreshes make no model calls. Observed POST-search recipes still launch a browser to reconstruct the anonymous search. Failed portals with saved recipes get plain retries with repair disabled.

**Prioritized findings and fixes.** P1 means high impact on correctness or usable recovery; P2 means a coverage or robustness improvement. These are implementation priorities, not measured estimates of effort.

| Priority | Limitation and evidence | Proposed fix and acceptance check |
|---|---|---|
| P1 | **Category pages can pass as tenders.** `validate_candidate` establishes IDs and titles, while first-read health does not require evidence that a record represents an individual procurement notice. Both the saved live data and a new fixture reproduce this. | Add a page/record type gate: directory, search form, listing, individual notice, attachment, empty state, or block. Require corroborating notice evidence from a detail page or structured notice record. Use buyer/reference/date/deadline/document context as signals, not a rigid demand that every portal expose every field. Negative examples must include CPV directories, buyer directories, news, and navigation cards. Acceptance: the two 44-category outputs cannot become verified tender snapshots. |
| P1 | **A file is assumed immutable at its URL.** `store_documents` reuses an existing file whenever its stored path exists. The probe's second read makes no HTTP request, so a revised specification at the same URL remains invisible. | Store validators and `last_verified_at`; use conditional GET with ETag/Last-Modified, plus periodic re-download when validators are absent or unreliable. Keep revisions by content hash and record which revision was current at each read. HTTP conditional validation is standardized in [RFC 9111, section 4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3). Acceptance: same URL, changed bytes produces a new revision and a tender change event. |
| P1 | **Missing from the result set means closed.** The database closes every previously stored, non-closed notice absent from the new snapshot. Health tolerates a moderate count drop. A four-to-three fixture passes health and closes the fourth notice without closure evidence. New notices can also conceal losses because the check compares counts. | Store `last_seen`, `missing_since`, source status, and observation status separately. Recheck the missing notice's detail page and require authoritative closure/deadline evidence. Treat changed search scope separately. Multiple complete observations can establish “no longer listed,” but should not by themselves prove a contract closed. Acceptance: a live notice moving outside a latest-results window remains open or unknown, with its absence recorded. |
| P1 | **A bounded result window is treated like the entire monitored population.** A URL such as “latest ten” can be read completely while still omitting older open notices. Pagination completeness cannot resolve this. | Save an explicit monitoring scope: latest window, current open opportunities, filtered results, or historical corpus. Maintain known active notices beyond the discovery window. Display exactly what the source covers. Never silently add a filter to make attachment succeed. |
| P1 | **Manual refresh cannot restart repair after failure.** `_handle` sets `allow_repair=False` whenever state is `failed`, including manually queued runs with a saved recipe. The probe confirms this. | Distinguish scheduler retry, user refresh, explicit repair, and relearn commands in the queue. Keep automatic retry cost limits, but provide a budgeted operator repair/relearn action. Acceptance: after a failed repair, an explicit repair action can create and validate a new candidate. |
| Fixed upstream | **Historical: repair could not handle an allowed API-child-host recipe.** At `a890ad9`, attach permitted `api.portal.example`, while repair returned before discovery. Persisting entry, listing, API, and attachment origins as separate roles remains a useful architectural improvement. |

The probe returns 20 rows, 19 unique notices, advertises 20, and passes health. | Count unique identities for collection coverage; track duplicate/conflicting observations separately. Prefer stable cursor/snapshot traversal when available, or overlap and reconcile offset pages. Fail or mark coverage uncertain when totals and distinct IDs disagree. Cursor pagination and changing offset results are discussed in the [GraphQL pagination guide](https://graphql.org/learn/pagination/). Acceptance: the 20/19 fixture cannot claim complete coverage. |
| P1 | **An anonymous search recipe does not identify its operation.** `SearchPages.open` matches endpoint, media type, and numeric paging shape. Two GraphQL operations at one endpoint can match the same saved recipe. The fixture reselects categories instead of tenders. | Save a sanitized operation identity: operation name, normalized query hash, filter/sort schema, result collection path, and expected record shape. Rehydrate tokens and cookies each visit; never persist them in the recipe. Acceptance: several operations sharing `/graphql` always select the intended tender operation. |
| P2 | **Empty is always unhealthy.** Both attachment validation and health reject zero notices, even when the source explicitly reports zero results. The empty-result probe confirms the health behavior. | Add a verified-empty outcome supported by the same search scope, healthy page structure, and a genuine empty-state signal or authoritative zero count. Distinguish empty, blocked, selector failure, and incomplete. Keep an unverified empty site pending until its recipe can be proven or a platform template supplies sufficient evidence. |
| P2 | **Some records can disappear during normalization without failing the read.** An ID rate of exactly 80% passes health; the four-out-of-five fixture is accepted. Detail 404/410 skips also disappear before the worker's raw count is constructed. | Account for every discovered row through each stage: extracted, duplicate, removed at source, invalid identity, detail failure, normalized, published. Show exclusion reasons and preserve valid notices as explicitly partial data if useful. Never call the snapshot fully verified while unexplained rows are missing. |
| P2 | **The recipe cannot compose list and detail sources.** Once a detail page is followed, all fields are extracted from that source. A buyer only present in the list is lost. A JSON list also forces its detail response through the JSON parser, so JSON-to-HTML enrichment fails. Both are reproduced. | Give each stage its own transport and parser. Let each field choose an ordered source list: list row, detail DOM, structured payload, attachment metadata. Preserve provenance and disagreements. Acceptance: JSON listing + HTML detail + buyer from the listing works in one recipe. |
| P2 | **Unknown status defaults to open; date-only deadlines are discarded.** The probe supplies `awarded` and an old date-only deadline and receives `open` with no deadline. Avoiding a fabricated deadline time is good, but losing the source date and asserting openness is not. | Preserve raw status, raw date, date precision, timezone provenance, and parse outcome. Add unknown/awarded internally or expose an auxiliary interpretation without silently changing the existing API contract. Use a date-only field instead of inventing midnight. Add localized dictionaries backed by fixtures. |
| P2 | **Replay can alter the originally observed search window.** `ObservedSearch.read(0, 0)` replaces a captured numeric offset such as 100 with zero. Reproduced by the probe. | Preserve the observed base offset, or explicitly classify the request as a later batch and rediscover the collection's first request. Store intended query scope independently of paging state. Acceptance: replay never silently changes the selected result set. |
| P2 | **Page count is a hard capability ceiling.** Both ordinary reads and candidate validation stop at 100 pages. BOAMP's configured feed exposes three records from a roughly 1.7-million-record collection; Ireland and Malta also hit page limits in the saved run. | Split initial backfill from continuous monitoring. Persist checkpoints and apply page/request/time budgets per slice. Where supported, partition by explicit publication intervals, buyer, or notice type with overlap and reconciliation. Ask for a narrower scope only when the original scope cannot be fulfilled; raising the cap alone leaves cost and consistency problems. |
| P2 | **Navigation has little room to recover from a bad choice.** At most two model-guided navigation steps, 60 links, 16,000 characters, one preferred detail sample, and a small proposal budget. Navigation calls also consume the weaker-model proposal allowance. | Search a bounded graph of candidate pages, classify page types, and backtrack. Allocate separate navigation, extraction, browser, and validation budgets. Expand evidence only around unresolved decisions. Preserve form actions, hydration/JSON-LD data, empty-state elements, and pager evidence before removing scripts or truncating markup. |
| P2 | **Browser discovery supports a subset of real interactions.** It loads the page and may scroll once; it does not learn general search-button, filter, tab, or next-button sequences. Support cursor state, public form state, and browser DOM extraction as separate execution capabilities. |
| P2 | **Feed discovery and replay have different capabilities.** Browser discovery forwards selected GET request headers and uses a visit cookie jar, but a plain GET feed recipe saves only the URL/selectors. | P2 | **Document coverage is poorly separated from notice coverage.** All linked documents being blocked fails the portal; zero detected document links on first attach can pass. **The next algorithm should attach a proven source contract, not just selectors.** A useful design is:

`discover candidate sources → classify page/record types → compile typed read plan → validate scope, identity and fields → publish coverage-qualified snapshot → monitor changes → repair the failing capability`

The source contract would record the user-requested scope, chosen collection, allowed origins, anonymous session bootstrap, pagination semantics, stage-specific parsers, field provenance, identity rules, empty-state evidence, completeness criteria, and document access rules. Model output remains a restricted declarative plan; it should not become arbitrary executable code. Ordinary reads still use no model.

**Additional idea portfolio.** These are proposals, not capabilities the current reader already has. They complement the concrete fixes above.

1. **Platform fingerprints and reusable recipe families.** Identify repeated procurement software through DOM structure, endpoint shapes, and public assets. Try a versioned family recipe, then learn only the buyer-specific differences. Require local validation so a family match cannot transfer an invalid assumption.
2. **A ranked set of source candidates.** Keep multiple listing/API candidates with evidence and cost estimates rather than committing to the first plausible page. Discard category and navigation candidates early.
3. **Structured-data discovery before model inference.** Inspect documented/public export links, JSON-LD, embedded application state, RSS/Atom, XML, CSV, and sitemaps. Map only demonstrated formats; do not assume every feed has tender semantics.
4. **One-click teaching.** Let an operator identify one actual notice and one reference/deadline/document region. Use those as anchors for learning and generate a reviewable extraction preview.
5. **Representative sampling.** Sample first/middle/last pages and cluster by DOM/record shape. Include notices with no files, multiple lots, amendments, older dates, and different statuses rather than only the first three records.
6. **A held-out validation set.** Learn on one group of notices and test on another. Include a later page never shown to the model. This reduces recipes that fit one sample's accidental layout.
7. **Evidence attached to every field.** Retain source URL, fetch time, selector/path, raw value, parser version, and a short source excerpt or hash. “Why did Watchtower say this?” becomes answerable.
8. **Confidence as several independent measurements.** Show identity confidence, field coverage, listing completeness, freshness, and document coverage separately. A single percentage can conceal a fatal weakness.
9. **A separate publish gate for semantic quality.** Keep operational status and data quality separate. A transport can work while record type is uncertain; a source can be offline while its last verified snapshot remains useful.
10. **Adversarial negative fixtures.** Add categories, footer links, product catalogs, news cards, related-notice widgets, cookie notices, and login pages with public menus. Measure false positives explicitly.
11. **Mutation-based recipe testing.** Move columns, add a banner, duplicate a CSS class, reorder cards, change punctuation, and introduce hidden elements. Compare extracted identities and fields. Use semantic invariants rather than brittle markup equality.
12. **Metamorphic completeness tests.** Adding an unrelated sidebar must not change tender count; splitting a list across pages must not change its unique identities; overlapping pages must not imply extra coverage.
13. **Multiple selector candidates with disagreement detection.** Compile a primary selector and evidence-backed alternatives. Switch only when validated; disagreement should trigger review or repair rather than silent fallback.
14. **Notice-type-aware schemas.** Model prior-information, contract, award, cancellation, and amendment notices distinctly. A publication without a submission deadline may be correct for its type.
15. **A relationship graph for notice identity.** Connect procurement process, notice, lot, amendment, and external reference. Do not collapse lots or amendments because they share a title or buyer reference.
16. **Cross-source corroboration.** Compare a buyer portal with an official aggregator/export when shared identifiers exist. Record disagreements and preserve provenance; neither source should silently overwrite the other.
17. **Incremental discovery plus active-notice surveillance.** Discover new notices from recent-result windows while revisiting known active notices for amendments and closure. This separates discovery coverage from lifecycle tracking.
18. **Adaptive polling.** Refresh active notices near deadlines more often, quiet archives less often, and back off on rate limits. Keep a maximum staleness target and occasional full reconciliation.
19. **Conditional page fetching.** Reuse unchanged HTML/JSON using validators, with cache keys that include scope, negotiation headers, and session-sensitive context. Preserve correctness around varying responses.
20. **A stable document identity distinct from the URL.** Signed URLs can rotate while bytes remain identical; stable URLs can serve new revisions. Track logical attachment, observed URL, and content hash separately.
21. **Document change summaries.** After byte-level revision detection, extract text and summarize changed clauses, deadlines, or quantities with page references. Start with deterministic text diffs; keep uncertain OCR separate from verified source facts.
22. **Shared attachment storage.** Deduplicate identical bytes across notices while preserving each notice's link, filename, access status, and revision history. This can reduce storage without merging tender identities.
23. **Browser session reuse within one attach attempt.** Discovery, sample validation, and the first full POST-search read can share an isolated visit and response cache. The current GET cache does not eliminate repeated browser/POST reconstruction.
24. **A bounded browser worker pool.** Browser startup and memory need their own concurrency budget. HTTP workers should not all launch Chromium at once. Keep per-portal session isolation.
25. **Checkpointed ingestion.** Persist the last committed page/cursor and coverage interval. Resume interrupted backfills rather than restarting them, while detecting expired cursors and changed scope.
26. **Staged publication.** Stream observations into a run-specific staging area, validate them, then publish atomically. Large portals need not accumulate every raw/detail record in memory. Incomplete runs must never trigger mass closure.
27. **A full run budget.** Limit elapsed time, requests, bytes, browser operations, model spend, and memory per run. The 100-page cap does not bound detail volume: 100 pages × 50 details gives roughly 5,100 requests, about 94 minutes at 1.1-second spacing before latency or files.
28. **Freshness deadlines and fair scheduling.** Schedule by expected work and staleness rather than only fixed intervals from the last start. A long-running portal should not immediately monopolize another refresh slot.
29. **Repair the smallest broken component.** A changed deadline label should repair a field selector, not rediscover the entire portal. A moved API should repair transport without changing IDs. Preserve unrelated verified parts.
30. **Shadow candidate recipes.** Run a repair candidate alongside the incumbent on the same snapshots and compare identities, missing values, and documents. Promote only after passing invariants; retain an immediate rollback target.
31. **A sanitized replay bundle for failures.** Save minimal pages/responses, selectors, type labels, counts, and error traces sufficient for offline reproduction. Redact cookies, tokens, and sensitive query values.
32. **A capability report at attachment time.** Explain “notices supported; attachments restricted; monitoring latest 20; historical coverage unavailable” instead of one broad success/failure message.
33. **Feedback that creates tests.** When an operator corrects a category mistaken for a tender or a wrong deadline, save the sanitized example as a regression fixture and update the relevant platform recipe.
34. **Separate discovery and truth benchmarks.** Report attachment rate, record-type precision, unique-notice recall within stated scope, field accuracy, document freshness, repair recovery, wall-clock time, and spend. More `serving` portals alone is the wrong target.
35. **Cost-aware exploration.** Prefer cheap deterministic probes, then targeted model evidence, then browser interaction. Escalate model capability for unresolved semantic/navigation questions rather than retrying unsupported pagination with a larger model.
36. **Explicit parser-loss diagnostics.** Record “source absent,” “selector missed,” “ambiguous,” “unsupported date precision,” and “invalid value” separately. Null alone hides whether the site or the reader is responsible.

**Suggested implementation order.**

| Sequence | Deliverable | Success criterion |
|---|---|---|
| 1 | Semantic record validation, stage accounting, verified-empty handling, and separate coverage reporting | Category fixtures cannot publish as tenders; legitimate zero results and excluded rows are explained accurately. |
| 2 | Document revalidation, missing-notice semantics, and operator repair control | Same-URL amendments are detected; a disappearing open notice is not automatically closed; failed recipes can be repaired deliberately. |
| 3 | Unified origin/session rules, operation identity, and list/detail composition | Child-host API repair, shared-endpoint GraphQL selection, negotiated GET feeds, and mixed JSON/HTML enrichment all pass isolated fixtures. |
| 4 | Explicit scope, cursor/form paging, stable identity reconciliation, and resumable ingestion | Large and moving collections are monitored without silent truncation, duplicate-count completeness, or excessive restarts. |
| 5 | Reusable platform recipes, adaptive sampling, incremental refresh, and shadow repair | Higher verified attachment rate at measured lower cost, with no increase in false positives. |

For each step, convert the relevant diagnostic probe into a desired-behavior regression test. Add fixtures from the failed real portals where redistributable source evidence is available. Rerun the ten-portal benchmark with a recorded commit, scope, budget, and independent output audit; compare against the audited one-of-ten baseline rather than the misleading three-of-ten state count. A fresh run requires external requests and model spend, so this review relies on the recorded run and offline verification.
